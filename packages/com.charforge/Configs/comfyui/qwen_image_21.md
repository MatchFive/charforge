# 路线 B：Qwen-Image-2.1（原生 RGBA 透明通道）

> 结论先说：**能跑，而且它解决了本项目最脏的一环；但它现在还补不上"四向一致性"那一环。**
> 所以定位不是"替换 SD1.5"，而是**并行的第二条路线**——见文末的分工建议。

## 一、你这张卡该怎么下权重

`Qwen-Image-2.1` 不是一个文件，而是**三个**（外加一个可选的提示词增强器，本仓库的工作流不带它）：

| 组成 | 作用 | 文件 |
|---|---|---|
| 7B 单流 DiT | 出图的扩散主干 | `qwen_image_2.1_int8_convrot.safetensors` |
| Qwen3-VL 8B 文本编码器 | 读提示词，**也是它能看懂中文和参考图的原因** | `qwen3vl_8b_int8_convrot.safetensors` |
| 64 通道 RGBA VAE | 四通道，透明度从这里来 | `qwen_image_2.1_vae_bf16.safetensors` |

**"transformer 不到 15G"这句话最容易误导人的地方就在这**：7B 主干 BF16 是 13.25 GB，看着刚好卡进 16 GB；但**文本编码器是另一个 8B 模型**，BF16 下 16.33 GB——单它一个就爆卡。两者相加 BF16 是 30.84 GB。

按权重总量分档（数字为磁盘占用，加载后大致相当，激活值另算）：

| 组合 | DiT | 文本编码器 | VAE | 合计 | 16 GB 可用？ |
|---|---|---|---|---|---|
| 官方 BF16 | 13.25 | 16.33 | 1.26 | **30.84 GiB** | ✗ 差一倍 |
| ComfyUI INT8 + INT8 编码器 | 6.76 | 8.71 | 0.63 | 16.10 GiB | △ 贴边，易 OOM |
| GGUF Q8_0 + Q8_0 编码器 | 7.12 | 8.11 | 0.63 | 15.86 GiB | △ 贴边 |
| **INT8 DiT + W4A8 编码器** | 6.76 | 5.88 | 0.63 | **13.27 GiB** | **✓ 推荐** |
| GGUF Q4_K_M + UD-Q4_K_XL | 3.91 | 4.80 | 0.63 | 9.34 GiB | ✓ 有余量，质量有损 |

**给你的 4070 Ti SUPER 16 GB 的结论：走第四行。** 同档 16 GB 卡的实测口径是峰值约 12–14 GB，
1024×1024 / 20–25 步约 25–35 秒每帧。权重合计 ≈13.3 GB，磁盘上三个文件约 17 GB。

不建议一上来就用 BF16，也不建议为了"省心"直接掉到 Q4——**Q4 会把 8B 文本编码器的语义能力削掉**，
而那正是你要用它读"南宋""龙泉窑"的部分，得不偿失。

### 后缀里的 W4A8 是什么

`W` = 权重（Weight），`A` = 激活（Activation）。**W4A8 = 权重 4 bit、激活 8 bit**，
是一种**非对称**的混合精度量化：

- **权重压到 INT4**：权重是训练后固定的静态张量，分布可控，压 4 bit 掉的主要是存储——相对 FP16 省约 75%。
- **激活保留 INT8**：激活是前向传播中随输入变化的中间结果，含离群值，再往下压会明显伤数值稳定性。

两者在同一个混合精度算子里相乘（INT4 权重 × INT8 激活，INT32 累加），
所以不会出现"权重压到 4 bit、激活被迫跟着压"这种连锁降级。

同一支 8B 文本编码器的三档（体积按 GiB；HF 页面另按十进制 GB 显示，数值约为 ×1.074）：

| 后缀 | 含义 | 体积 | 语义保真 |
|---|---|---|---|
| `bf16` | 全精度 | ≈16.33 GiB | 满 |
| `int8_convrot` | 权重与激活均 8 bit，ComfyUI 模板默认 | ≈8.71 GiB | 几乎无损 |
| `w4a8` | 权重 4 bit + 激活 8 bit | ≈5.88 GiB | 略降，仍可用 |

对文博场景，这一档差异落在**考据词项的语义保真**上——「南宋」「龙泉窑青釉」「开片」这类词，
编码器压得越狠，语义越容易被抹平，出图就只剩一个"古装人"的空壳。

> **两个容易混的文件要分清**：**主编码器**写作 `qwen3vl_8b_w4a8.safetensors`（本仓库推荐的那一支）；
> 而 `qwen3.5_9b_qwen_image_2.1_pe_t2i / pe_i2i` 是**提示词增强器（PE）**，
> Comfy-Org 官方只发布了 `int8_convrot` 一档，带 `_w4a8` 后缀的属社区量化版，来源需自行核对。
> 本仓库的工作流**不包含 PE**（见第二节），所以那个文件当前不用下。

### 前置条件（不满足会以各种奇怪方式失败）

| 条件 | 说明 |
|---|---|
| ComfyUI **≥ 0.37.0** | 0.36 及以前**完全没有** Qwen-Image-2.1 节点，加载工作流会整片报"节点缺失" |
| PyTorch **cu130** | `int8_convrot` 的文件是给 CUDA 13 内核编的；CUDA 版本不够时 ComfyUI 会静默关掉这些内核，速度掉一截 |
| 用 GGUF 的话 | 必须换成 **leejet 版**的 `ComfyUI-GGUF`；用 city96 版会在加载时直接报错 |

模型放 `ComfyUI/models/` 下对应的子目录：`diffusion_models/`、`text_encoders/`、`vae/`。

## 二、怎么接到 CharForge

本目录已备好一对可直接用的文件：

```
charforge_qwen21_txt2img.workflow.json     # API 格式，扁平节点，能直接被插件提交
charforge_qwen21_txt2img.bindings.json     # 节点绑定
```

**这份工作流以 ComfyUI 官方模板「Qwen-Image-2.1 Text to Image」导出的 API 格式为准**，
生成链已在本机 16 GB 卡上实测出图。相对官方导出件只有三处改动：

| 改动 | 原因 |
|---|---|
| **剔除提示词增强器分支** | 官方模板带一整段 PE 分支（`TextGenerate` + 9B `CLIPLoader` + `PrimitiveStringMultiline` + `ComfySwitchNode`）。它会把中文考据词项改写成**英文段落**，反而丢掉「南宋」「龙泉窑青釉」的术语精度；且 16 GB 上主链路 13.3 GiB 再加一支 9B 编码器必然换页。 |
| **节点重编号为 1–10** | 官方导出件的 id 形如 `459:452`（subgraph 展开残留），重编号后绑定文件可读。 |
| **输出前缀改 `charforge/qwen21`** | 便于在 `ComfyUI/output/` 里定位本项目产物。 |

**为什么必须用扁平 API 格式**：官方模板把整条生成链包在一个 **subgraph** 节点里，
而 **subgraph 不能被 `/prompt` 接口直接提交**——硬提交只会得到一个含糊的报错。
这是它和 SD1.5 工作流最大的形态差异。

三处**不要动**的地方：

- **节点 4 `ResolutionSelector`** 是尺寸的唯一来源（1:1 / 1 MP → 1024×1024）。
  改分辨率只改这里。`bindings.json` 里**刻意没有** `width` / `height`——
  节点 5 的宽高是**链接**，一旦绑定就会被替换成字面量（插件默认 512），
  等于逼 Qwen 在低于它训练区间的尺寸上出图。
- **节点 6 `TextEncodeQwenImage21`** 正负提示词挂在**同一个节点**上（取输出 0 / 1），
  字段名是 `prompt` / `negative_prompt` 而不是 `text`——绑定文件已显式指明。
- **节点 10 `SaveImageAdvanced`** 的 `format` 必须是 `png`。存 JPG 会把 alpha 直接丢掉。

顺序（不要跳步）：

1. 先在 **ComfyUI 界面里手工 Queue 一次**这份工作流，确认能出图；
   这一步不能跳过——否则插件只会给你一个超时错误，看不出真正原因。
2. 确认输出是**带透明背景的 PNG**（见下一节）。
3. 插件窗口「后端设置」：地址填**本机 ComfyUI 实际监听的端口**——本机 Desktop 版是 **`http://127.0.0.1:8000`**
   （启动参数 `--port 8000`，2026-10-12 实测确认）。**不是 8188**：本机 8188 无任何监听，填错的表现是
   「探测后端」失败。插件设置项是 `ComfyUiUrl`，默认值 8188 是通用约定，Desktop 版要改。
4. 工作流指向这个 JSON 的绝对路径。
5. 点「探测后端」应显示 `ComfyUI 就绪`，然后点「生成并装配」。

## 三、它对本项目的三个真实差异

### 1. 原生 alpha —— 抠图这一环自动让路

官方推荐的提示词写法是**首尾各加一句**，这正是工作流里已经写好的：

```
This is an RGBA image with transparency. … The image has alpha channel and the background is transparent.
```

（必须存 PNG，存 JPG 会把 alpha 丢掉。）

**实测（2026-10-12，首图）补一条官方句式没写的**：只写上面两句，Qwen 会**自作主张在脚下画一片椭圆投影**——影子是半透明的，会跟着 sprite 进四向动画，每帧形状还不一样，帧间抖动由此而来；北向（背面）帧的影子也照画在脚下。提示词里必须显式加一句否定，例如：

```
无地面，无投影，脚下是看不见的地面；no ground, no shadow, no floor.
```

同一张首图的 alpha 实测数据（1024×1024，可作后续对照基线）：四角 alpha 全 0、
83.8% 像素透明、角色本体占画布 27.9%、水平中心 x=513（画布 512 处），透明是**真透明**。

**画风路线**：v0.4.3 起为**华丽精致的半写实厚涂**——光影层次、材质区分（布料/皮革/金属/木料）、
饰件细节、轮廓边缘光。首版（2026-10-12）曾定为扁平赛璐璐，后放弃，理由是**画风解耦**：
第 2 步的 Spritely Sheet LoRA 会把角色统一转成 `32-bit pixel art`（骨架图配套 .txt 里那句是固定
措辞），立绘只作槽 10 的身份参考图，它的画风根本不进成片。既然立绘不背像素风的包袱，
就没有理由为了「统一」把它压成扁平色块——反而白白丢掉光影与材质的信息量。

> 唯一不能破的底线是**材质与轮廓可辨**：发色、服饰形制、主配色必须一眼读得出来。
> 华丽到把结构糊掉，第 2 步的 identity 参考就会走形。

Qwen 默认出写实照片感，缩到 512 画布会糊；工作流节点 6 的默认提示词与插件常量
（`PromptForgeService.StylePrefix`）**逐字一致**（已用脚本比对），可作后续各帧的模板。
改画风时两处必须同步——不一致不会报错，只会让「在 ComfyUI 里手工排队」与「插件出的图」
悄悄变成两种画风。

这一步的价值比"多一个抠图功能"大得多：**透明度属于生成模型本身，而不是事后补救**。
我们上一版加的那个 `LocalMatting` 色键兜底会因为"检测到已有 alpha"而**原样放行**，
不会去破坏它——也就是说这条路是干净的，不是绕过去的。

而且它直接治好了上一版那个碰撞体缺陷的**根因**：`FrameNormalizer` 是按 alpha 裁切并量包围盒的，
真 alpha 进来，量出来的就是角色本身；不会再有"包围盒等于整幅画布"这种事。

### 2. 中文提示词直接进模型 —— 术语表在这一路不是必需的

`qwen3vl_8b` 是多语言视觉语言编码器，**支持中文与中英混排**。
所以 `Configs/prompt_glossary.json` 那套"中译英"在这一路**不是必需品**——
它是为 SD1.5 的英文 CLIP 词表才存在的。

对文博场景这是实打实的收益：「南宋」「龙泉窑青釉」「开片」这些词，
**让它直接读原文，比先翻成英文再喂给只认英文的编码器要准**，也省掉了一层语义损耗。

（一处待改：流水线目前对 ComfyUI 后端**无条件**跑术语表，并会对残留中文发告警。
换到 Qwen 后那条告警是**误报**——中文在这一路能进模型。见文末待办。）

### 3. 生成 1024、画布 512 —— 所以绑定里**故意不绑宽高**

Qwen-Image-2.1 的建议总像素量是 **100 万到 400 万**，而项目的画布是 512×512 = **26 万**，
低于下限一个数量级。所以正确做法不是"逼它出 512"，而是：

```
Qwen 出 1024×1024  →  FrameNormalizer 按 alpha 裁切、盒式降采样到 512 画布
```

`bindings.json` 里因此**没有** `width` / `height`：节点 5 保持 1024，缩放交给流水线。
如果你把宽高绑上，就等于强制它用 512 出图，质量会明显掉。顺带一提边长要是 16 的倍数（建议 32）。

### 4. 图生图（Image Edit）：把风格母版喂回去锁角色

`charforge_qwen21_img2img.workflow.json` 是同一模型的**编辑**工作流，关键机制有三个：

- **生成与编辑合一**：同一套 DiT / 编码器 / VAE 权重，编辑能力由
  `TextEncodeQwenImage21` 的参考图槽位（`image_1`…最多 16 个）承担，
  **不需要下载任何新模型**。
- **初始潜空间跟随参考图**：编码节点输出 2 是按 `image_1` 几何生成的潜空间，
  KSampler 直连它（官方模板经 `ComfySwitchNode` 切换「跟随参考图 / 自定义画布」，
  本工作流删掉开关恒取前者）；`resolution=0` 表示参考图按原尺寸（32 取整）参与编码。
  这就是编辑不跑构图的原因。
- **插件接入**：参考图走「姿势模板」字段（`FrameRequest.PoseTemplatePath` →
  `load_image` 绑定），插件经 `/upload/image` 逐帧重写 `LoadImage` 节点。
  在本工作流里这个字段的语义是「风格/角色参考图」，不是骨骼骨架。

提示词按索引引用槽位图（单图时直接写「image_1 中的人物」即可），指令要写清
**「改什么、其余保持什么」**——风格母版（`qwen21_00002.png`）定的画风、
青灰长衫、无影子条款都要在指令里声明「保持不变」，否则编辑会自由发挥。
（此处的槽位指令已于 v0.4.3 去掉具体画风名：母版换过画风就会说谎，改写成中性的「与画风完全不变」。）
PE 增强器（`..._pe_i2i`）已按 t2i 同口径整段移除。

## 四、它现在还做不了的事：姿势锁定（这是关键）

四向一致性靠的是 ControlNet 锁姿势，而：

- **`Qwen-Image-2.1-Fun-ControlNet-Union` 确实存在**：一个约 7.5 GB 的控制分支，
  含 Pose（DWPose 骨架）在内共 8 种条件 + 局部重绘，以 `strict=False` 挂在冻结的主干上。
- **但它的 ComfyUI 支持还没并入稳定版**（PR #16519 仍在 review 中）。
  现在只有 Kijai 的实验性补丁，或走官方的 VideoX-Fun（Python 侧，不在 ComfyUI 里）。
- 即便并入了，**7.5 GB 控制分支 + 13.3 GB 权重 ≈ 21 GB**，16 GB 上必然大量换页，
  速度会难看到不能用于批量出 16 帧。

**结论：这一路现在解决"资产干净"，解决不了"四向一致"。**

| `steps` | 25–40 | 官方默认 40，模板 25，25 步已可用 |

| `scheduler` | `simple` | |
| `denoise` | 1.0 | |

另外两条反直觉的：**模型是 LLM 编码的**，所以

- 提示词权重语法（`(word:1.2)`）**不生效**，会被当成普通标点；

## 八、两条路线怎么分工（建议）

| | 路线 A：SD1.5 + ControlNet | 路线 B：Qwen-Image-2.1 |
|---|---|---|
| 定位 | **一致性主力**：16 帧、四向、靠骨架图锁姿势 | **资产与合规主力**：单帧母版、干净 alpha、中文考据 |
| 四向一致性 | ✓（已可用） | ✗（ControlNet 未并入稳定版） |
| 透明通道 | 需本地抠图兜底 | ✓ 原生 |
| 中文提示词 | ✗ 必须译英 | ✓ 直接可用 |
| 许可 | 宽松 | 非商用，需授权 |
| 速度（16 帧） | 约 1 分钟 | 约 7–10 分钟 |

**可执行的下一步（按顺序）：**
